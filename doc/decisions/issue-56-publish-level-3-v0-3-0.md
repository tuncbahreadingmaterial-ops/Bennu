# Issue #56 — Publish Bennu Level 3 as v0.3.0

- **Issue:** https://github.com/tuncbahreadingmaterial-ops/Bennu/issues/56
- **File status:** Active append-only decision record

## 2026-07-26 — Separate the stable Level 3 candidate from production publication

- **Context:** The exact accepted Level 3 implementation on `main` is ready to become a stable `0.3.0` release candidate. The repository's authoritative version input is also consumed by the CLI identity, build metadata, Windows resource, packages, provenance, and publication contracts. Selecting a stable version must not itself create or authorize a production tag or release, and the already published `v0.1.0` and `v0.2.0` artifacts must remain immutable.
- **Decision:** Set the sole root `VERSION` input to exact LF-terminated `0.3.0`, update its exact-byte contract, and describe the source tree as the stable `v0.3.0` release candidate. Keep candidate preparation separate from production publication: this change creates no tag or release, does not dispatch the release workflow, and does not authorize later mutation without a separate exact-candidate readiness decision. Level 3 release highlights are typed scalar program parameters and portable argument decoding; structural tuples with static one-level primitive-prefix spreading; explicit deterministic sequential fan-out; value-independent lowering with profile-v2 accounting and borrowed multi-consumer liveness; generated strict-C11 and native parity; checked Int64 arithmetic with controlled binary64 behavior; expanded Boolean, predicate, and numeric-ordering primitives; ordinary long-path support on Windows; and warning-free protected three-platform CI with reproducible release provenance.
- **Alternatives considered:** Publish directly when changing `VERSION`; retain `0.2.0` until a production tag is created; create a prerelease SemVer identity; or expand the candidate with later validation, packaging, signing, or Level 4 work. Direct publication would collapse independent readiness and public-state verification into preparation, retaining the old identity would make candidate binaries and provenance false, a prerelease identity would not match the accepted stable release contract, and scope expansion would invalidate the frozen Level 3 boundary.
- **Rationale:** A stable but unpublished candidate lets every build, package, manifest, refusal path, platform CI run, and independent verifier observe the exact intended product identity before any immutable public mutation. Keeping publication as a later success-gated step preserves the repository's fail-closed trust model and makes the absence of `v0.3.0` public state an explicit candidate invariant.
- **Consequences or follow-up:** Candidate executables report exactly `bennu 0.3.0`, while production remains unpublished. The release workflow, publisher, provenance implementation, platform set, runtime behavior, historical releases, and trust policy are unchanged. New Level 4 language behavior, additional platforms, installers, package-manager publication, Authenticode, Apple Developer ID/notarization, and mutation or rebuilding of `v0.1.0` or `v0.2.0` are non-goals. Independent readiness verification, exact-head three-platform CI, a non-publishing candidate workflow run, separately authorized production publication, independent public-asset verification, and terminal Issue #56 reconciliation remain follow-up stages.
- **Validation/evidence:** The stable-version exact-byte contract, `bennu --version`, documentation smoke checks, release/workflow/provenance contracts, and publication-refusal state machines bind candidate identity and separation from publication. Complete ordinary Release, strict, isolated QA, exact-head three-platform CI, and a non-publishing Future Release Candidate run provide the remaining staged evidence. Per owner direction, ASan/UBSan checks may be omitted and no sanitizer acceptance is claimed.
